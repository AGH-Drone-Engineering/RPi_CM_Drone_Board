= CMDB Firmware Tools

Software running on the Raspberry Pi Compute Module side of the drone board, talking to the onboard ESP over LoRa/UART.

== loracom

CLI tool for talking to the ESP: send a message, read a queued message, or request its configuration. Timeout and retry behavior are configurable — run `loracom --help` for the full flag reference. The UART device is not: it is compiled in as `/dev/ttyAMA3` (`DEFAULT_DEVICE` in `main.cpp`), the port `install-loracom.sh` enables. For the wire protocol itself, see `loracom/protocol.adoc`.

`--message` is limited to 248 bytes — the ESP's default 256-byte UART RX buffer minus the 8-byte frame overhead (header + checksum). A longer message is rejected with `-EMSGSIZE`, no bytes sent. Use `--force` to ignore that check.

All errors are returned as negative `errno` codes (see `errno(3)`) — e.g. `-ENODATA` (queue empty), `-EMSGSIZE` (message too long), `-EREMOTEIO` (no response from the HAT after retries), `-EINVAL` (bad arguments), `-ENODEV` (the UART device doesn't exist — UART3 isn't enabled, see `system-setup.sh`), `-EBUSY` (another `loracom` instance is using the port). Run with no options at all and you get the help on stderr and `-EINVAL`.

Only one `loracom` transaction runs on the UART at a time — instances take an `flock` on the device before opening it. An instance that finds the port busy waits for the timeout and retries, up to `3 * (retries + 1)` times, then gives up with `-EBUSY`. That budget is deliberately at least as long as the worst case the instance holding the port may take (`retries + 1` attempts, each up to three timeouts long when checksums fail), so `-EBUSY` means "genuinely stuck", not "the other instance was retrying on a noisy link". Callers that poll in a loop should treat `-EBUSY` as "try again shortly", not as a link failure.

`loracom --help` prints the commit the binary was built from, so you can tell what's actually deployed on a board (`-dirty` means it was built from an edited working tree).

=== Using loracom from Python

`loracom` is a plain CLI tool, so Python just shells out to it via `subprocess` (which blocks until it exits). `--get` checks the current queue once and returns — it doesn't wait for a future message to arrive — so receiving needs a polling loop on the Python side.

[source,python]
----
import os, ctypes, errno, subprocess

# check drone ID
ID = os.environ["CMDB_ID"]

# send
subprocess.run(["loracom", "--send=5", "--message=hello from the RPi"])

# receive with error handling
while True:
    result = subprocess.run(["loracom", "--get"], capture_output=True, text=True)
    rc = ctypes.c_int8(result.returncode).value # exit codes arrive as unsigned bytes in Python
    if rc == -errno.ENODATA:   # queue empty
        continue
    if rc < 0:                 # any other error (e.g. -errno.EREMOTEIO)
        raise RuntimeError(f"loracom --get failed with errno {-rc}: {result.stderr.strip()}")

    sender_id = rc
    msg = result.stdout.rstrip("\n")
    # Handle msg...
----

== bootstrap

`cmdb-bootstrap.service` runs `bootstrap/bootstrap.sh` early at boot: it calls `loracom --config` and publishes every returned `KEY=VALUE` pair twice — through `systemctl set-environment` (for systemd units started afterwards) and into its own block in `/etc/environment` (for PAM sessions, e.g. SSH). Every step is best-effort: failures are logged, the boot continues.

From the ESP, always sent:

* `CMDB_ID` — the board's own LoRa address. Sets the hostname to `raspi-usa-<CMDB_ID>`.
* `CMDB_ESP_FIRMWARE_BUILD` — commit the HAT firmware was built from. Propagated only, nothing acts on it.

From the ESP, acted on if present:

* `CMDB_HOSTNAME_PREFIX` — replaces the `raspi-usa` prefix.
* `CMDB_GETCONF_TIMESTAMP` — unix timestamp to set the system clock to. *NOT IMPLEMENTED ON ESP SIDE.*
* `CMDB_POST_INIT_CMD` — command run after propagation, with all the variables in its environment. Currently unused.

Set locally by `install-cmdb-base.sh`, in a separate block of the same file:

* `CMDB_HARDWARE_REVISION=1`
* `CMDB_HARDWARE_TYPE=STANDARD`

=== Hostname

Tried in order, each falling through to the next. `<mac>` is the first non-loopback interface, hyphenated:

* `raspi-usa-<CMDB_ID>` — normal case.
* `raspi-usa-fallback-<mac>` — `bootstrap.sh` ran but got no usable `CMDB_ID`.
* `CMDB-<mac>` — written by `install-cmdb-base.sh` at provisioning time. Seeing it on a running board means it never reached the HAT.

`127.0.1.1` in `/etc/hosts` is kept in sync and `avahi-daemon` restarted, so `<hostname>.local` follows the current name.

== Installation

`sudo ./system-setup.sh` on a fresh CM5 image. It runs the four scripts below in order, then disables the onboard Bluetooth — `dtoverlay=disable-bt-pi5` in its own `config.txt` block, plus `hciuart.service`, which would otherwise keep trying to bring up a radio that isn't there. Nothing on the drone uses Bluetooth and its radio shares the 2.4GHz band with the WiFi the board is reached over. That's the only change `system-setup.sh` makes on its own; run it (or add the overlay by hand) if you provision a board with the install scripts individually. *Reboot afterwards* for the `config.txt` changes. Everything is idempotent, each script prints what it changes on start, and each is usable on its own — the normal way to redeploy after a change. `common.sh` is a sourced helper, not something you run.

=== install-cmdb-base.sh

* `/etc/environment`: `CMDB_HARDWARE_REVISION=1`, `CMDB_HARDWARE_TYPE=STANDARD`
* hostname: `CMDB-<mac>`, see <<Hostname>>
* `config.txt`: `dtoverlay=uart0-pi5` — GPIO14/GPIO15, giving `/dev/ttyAMA0`. That's `J_FC_UART` on the IARC HAT, i.e. the flight controller; a serial console on that device is disabled if one is enabled.
* `config.txt`: `usb_max_current_enable=1` — off the onboard buck nothing negotiates a PD contract, so the firmware caps all of USB at 600mA; this lifts it to 1.6A. Safe on USB-C too, since VBUS is limited to ~2.1A in hardware (U6). `PSU_MAX_CURRENT` is deliberately left out of the EEPROM: `CC1`/`CC2` run to the module, so on USB-C a contract really is negotiated.
* `cmdb-mavlink.service`: MAVProxy, enabled at boot

[source,sh]
----
mavproxy.py --master=/dev/ttyAMA0,57600 --out=udpin:0.0.0.0:14550 --out=udpin:0.0.0.0:14551 --daemon --state-basedir=/var/log/mavproxy
----

Device, baud and the port list are variables at the top of the script and the unit is generated from them — one `--out` per port in `MAVLINK_UDP_PORTS`. `udpin` listens rather than pushing to a fixed address, so point a GCS at `udp://<board>:14550` or `udp://<board>:14551`. MAVProxy itself comes from `install-utils.sh`.

=== install-utils.sh

* apt: `screen`, `build-essential`, `g++`, `make`, `git`, `curl`, `cmake`, `pkg-config`, `python3-pip`, `python3-venv`, `python3-dev`, `i2c-tools`, `minicom`, `avahi-daemon`, `xrdp`, plus kernel headers — the package name has moved across RPi OS releases, so it takes the first candidate the archive has
* pip, system-wide: `opencv-python`, `ultralytics`, `MAVProxy`
* VNC: `raspi-config nonint do_vnc 0`
* RDP: `xrdp` on 3389, serving its own Xorg session so it coexists with VNC
* Claude Code, for the `sudo` user

RDP also gets that user a `~/.xsession` (`startlxde-pi`) if there isn't one — Bookworm's session files are Wayland-only and xrdp would land on a black screen — and puts `xrdp` in the `ssl-cert` group. There's no key auth, so the account needs a password; the script warns rather than setting one.

=== install-cam.sh

Installs the whole camera stack for the *FRAMOS FSM:GO IMX900* on *CAM0*. The stock Raspberry Pi camera stack doesn't know this sensor, so all three layers get replaced:

. *Kernel* — installs the FRAMOS out-of-tree sensor and GMSL modules into `/lib/modules/<ver>/updates/drivers` and their device tree overlays next to `config.txt`, then *holds the kernel packages* (see below).
. *Userspace* — https://github.com/framosimaging/framos-libcamera[framos-libcamera], a libcamera fork carrying the IMX900 CamHelper and tuning files, plus `rpicam-apps` rebuilt against it, both under `/usr/local`. Replaces the distro `rpicam-apps` package. Skipped once installed — `CMDB_REBUILD_LIBCAMERA=1` forces a reinstall.
. *Firmware* — writes `dtoverlay=fr_imx900,cam0` to `config.txt` and turns `camera_auto_detect` off, since autodetect and an explicit sensor overlay fight over the same CSI port. Any hand-added `fr_imx900` line outside the block is commented out too, so the overlay can't be loaded twice.

After a reboot, `rpicam-hello --list-cameras` should show the sensor as `fr_imx900 [2064x1552 12-bit RGGB]`, with five modes under each of `SRGGB8` / `SRGGB10_CSI2P` / `SRGGB12_CSI2P`.

==== When it says "No cameras available"

The FSM:GO module carries a `tca6408` GPIO expander at `0x20` that `fr_imx900` depends on, and it is flaky on a cold start. If `dmesg` shows

[source]
----
pca953x 10-0020: probe with driver pca953x failed with error -121
i2c 10-001a: deferred probe pending: i2c: supplier 10-0020 not ready
----

then the expander NAKed (`-121` is `EREMOTEIO`) and the sensor never finished probing. Check `i2cdetect -y 10` first:

* *Devices answer* (`0x1a`, `0x20`, `0x36`, `0x56` show up) — a transient I²C glitch. `echo 10-0020 | sudo tee /sys/bus/i2c/drivers/pca953x/bind` completes the deferred probe and the camera appears without a reboot. It has come and gone between boots on the same board; wrap the rebind in a systemd unit if it becomes routine.
* *Bus completely empty* — nothing on the module is answering, and the rebind fails with the same `-121`. That's a cable or module-power problem, not software. This is the state `raspi-usa-1` was in as of 2026-08-01.

Layers 1 and 2 ship *prebuilt* in `cam-prebuilt/`, so a normal install copies files and takes seconds instead of the ~12 minutes the meson builds cost. Both halves are pinned — the modules to one exact kernel build, the `/usr/local` payload to one Debian release — so each is checked against the running system and *falls back to building from source* when it doesn't match. That fallback is what lets a board be provisioned from an image whose kernel isn't the one the payload was built on. `CMDB_CAM_FROM_SOURCE=1` ignores the payload entirely.

==== The kernel hold

The modules are pinned to one kernel build by their `vermagic`. An upgraded kernel gets its own empty module directory alongside the old one, so after the next reboot the sensor just doesn't probe — with nothing in the logs pointing at apt. `install-cam.sh` therefore runs `apt-mark hold` on the kernel meta-packages it finds installed (`linux-image-rpi-2712`, `linux-image-rpi-v8` and the matching `linux-headers-*`, or `raspberrypi-kernel*` on older images). `CMDB_HOLD_KERNEL=0` skips it.

The source fallback is *not* protection against this — nothing re-runs `install-cam.sh` at boot, so the board stays without a camera until somebody notices and runs it again. The hold is what prevents that; the fallback only makes the recovery cheap (just the modules rebuild — the `/usr/local` payload is pinned to the OS release, not the kernel). Nor is any of this a consequence of shipping prebuilt modules: without DKMS, modules built from source on the board are pinned to their kernel identically, and building on the board only helps at install time.

The held packages are *meta*-packages. The versioned ones (`linux-image-6.18.34+rpt-rpi-2712`) never upgrade in place — every kernel is its own package — so holding those would accomplish nothing; what carries a board forward is the meta's `Depends` flipping to the next version. The hold only blocks apt: `rpi-update` pulls kernels straight from GitHub, and reflashing the image obviously bypasses it.

To move to a newer kernel deliberately: `apt-mark unhold` the packages the script listed, `apt upgrade`, reboot, re-run `install-cam.sh` (which rebuilds the modules and re-applies the hold), and run `cam-prebuilt/make-prebuilt.sh` if that kernel is the one to ship.

The source path needs the kernel headers (`install-utils.sh`) and `dtc`, which it installs if missing; it clones framos-libcamera at the pinned branch `framos_v0.5.2+rpt20250903` — that fork is 16 MB of sources we carry no patches against, so it isn't vendored. Drop a checkout at `firmware_CMDB/framos-libcamera` to run the source path without reaching GitHub.

==== cam-prebuilt/

The prebuilt payload: `modules/fr_*.ko.xz`, `overlays/fr_*.dtbo`, `usrlocal.tar.gz`, and a `manifest` recording the kernel, arch and OS release they were built on — that's what `install-cam.sh` checks — plus the apt packages the payload needs at runtime, derived from the binaries themselves rather than hand-maintained, so regenerating on a new Debian release can't leave the consumer asking for the old release's sonames. Regenerate with `cam-prebuilt/make-prebuilt.sh` on a board where the stack was built from source; see `cam-prebuilt/README.md` for what is and isn't safe to touch (short version: nothing is stripped, because stripping an IPA module invalidates the signature libcamera checks at load time).

Overlays are plain DTBs with nothing pinning them to a kernel or an OS release, so those are used even on the source path — which is why `dtc` is normally not needed at all.

==== framos-rpi-drivers/

A vendored copy of https://github.com/framosimaging/framos-rpi-drivers[framos-rpi-drivers] (`v1.1.1`, branch `framos_20250916`), *patched* — which is why it's carried in-tree instead of cloned.

Without the patch *full resolution does not start at all* — `Format mismatch`, `Failed to start media pipeline: -22`. Upstream's `fr_imx900.c` declares a different Bayer order per mode (RGGB for the full-res and crop modes, GBRG for the subsampled ones), but libcamera picks one native order for the whole sensor: the numerically lowest advertised mbus code, which is `SGBRG10_1X10`. So it programs the CFE as GBRG while the subdev reports `SRGGB12` for 2064x1552, and the pipeline refuses to start. The GBRG labels are wrong anyway — the sensor emits RGGB in every mode, confirmed by Bayer-phase correlation on raw DNGs and by the sensor's own test pattern — so the subsampled modes that did start came out with swapped colour channels.

The patch drops the `SGBRG` entries, which makes `SRGGB10_1X10` the lowest code and settles libcamera on RGGB, and removes the `- 3` truncation so all five modes are exposed at each bit depth (upstream left binning crop reachable through neither code). Full detail, plus the caveats it introduces — notably that `--hflip`/`--vflip` stop working — in `framos-rpi-drivers/PATCHES.md`.

Only the tracked sources are kept — no `.git`, and build output is gitignored. To refresh it from upstream, re-clone, re-apply the `fr_imx900.c` change and copy the tracked files back over.

=== install-loracom.sh

* `config.txt`: `dtoverlay=uart3-pi5` — GPIO8/GPIO9, giving `/dev/ttyAMA3`, the port `loracom` uses to talk to the ESP
* `/opt/cmdb/bin`: `loracom`, `bootstrap.sh`
* `/usr/local/bin/loracom`: symlink, plus `/opt/cmdb/bin` on `PATH` via `/etc/profile.d/cmdb.sh`. The symlink is what makes `loracom` work from anything that never reads `/etc/profile` — systemd units, cron, `ssh board loracom --get`, `CMDB_POST_INIT_CMD`
* `cmdb-bootstrap.service`: installed and enabled, runs on the next boot

Builds as the `sudo` user, so `loracom/obj` and `loracom/bin` stay writable for ordinary `make` afterwards.

`install-cmdb-base.sh`, `install-cam.sh` and `install-loracom.sh` all edit `config.txt`, each in its own marked block — as does `system-setup.sh` for the Bluetooth overlay — so they don't interfere and can be run in any order or individually.
