# Prebuilt FRAMOS camera payload

What `install-cam.sh` installs instead of compiling. Generated by
`make-prebuilt.sh`; do not hand-edit anything here.

| path | what | pinned to |
|---|---|---|
| `modules/fr_*.ko.xz` | FRAMOS sensor + GMSL kernel modules | one exact kernel build |
| `overlays/fr_*.dtbo` | device tree overlays | nothing - plain DTBs |
| `usrlocal.tar.gz` | libcamera + rpicam-apps tree, unpacked over `/usr/local` | one OS release + arch |
| `manifest` | what the above were built on, and the apt packages they need | - |

`install-cam.sh` checks the manifest against the running system and falls back
to building from source when it does not match, so a stale payload costs time,
not a working camera. What each half is pinned to:

- **Modules** carry a `vermagic` and modversions CRCs tied to one kernel build.
  Any kernel change - a plain `apt upgrade` is enough - and they refuse to load.
- **`usrlocal.tar.gz`** links against release-specific sonames (`libavcodec61`,
  `libqt5core5t64`, `libboost-program-options1.83.0`), so it is good for the
  Debian release named in the manifest and no other.
- **Overlays** are compiled DTBs with no such coupling and are always used.

## Regenerating

On a board where the stack was built from source and works:

```sh
sudo ../install-cam.sh          # with CMDB_CAM_FROM_SOURCE=1 if it needs building first
./make-prebuilt.sh
```

`PREBUILT_RUNTIME_PACKAGES` is derived from the harvested binaries' `DT_NEEDED`
entries rather than written by hand, so it cannot name the previous release's
packages after a regeneration — the one drift the manifest's own checks would
not catch, since everything else in them would have been updated correctly.

Modules and overlays are rebuilt from `../framos-rpi-drivers` so the payload
provably matches the sources in this repo. The `/usr/local` half can only be
harvested from a live install - it comes from the file lists meson wrote to
`/opt/framos/*/build/meson-logs/install-log.txt`, plus the IPA `.sign` files,
which libcamera creates in a post-install step meson does not log.

Nothing in the payload is ever stripped. libcamera signs its IPA modules and
verifies them at load time against a public key baked into `libcamera.so`;
touching an IPA `.so` invalidates its `.sign` and demotes the IPA to running in
an isolated process.
